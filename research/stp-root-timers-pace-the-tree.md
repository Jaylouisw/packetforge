# Whose forward delay a non-root's ports run on

Question: a bridge's ports spend Listening then Learning before they forward. Which device's forward delay
sets that time - the answering bridge's own configuration, or the root's? The header lines of
`show spanning-tree` say the two sets are different on a non-root
([stp-timer-lines-source.md](stp-timer-lines-source.md)); this note is about which of them the *ports* obey,
because that is what the convergence schedule waits out.

## What the sources say

They say the same thing in four different voices, and none of them leaves the local value in charge:

1. **Cisco Learning Network, "STP timers"** - asked why a non-root's own timers appear in the Bridge ID block
   but seem to do nothing: "BPDUs carry the configured Root Bridge Timers Values. These BPDUs are generated by
   the Root Bridge and forwarded out all Designated Ports, so eventually all switches in the Spanning Tree
   topology learn and use such Timers Values, **ignoring local Timers Values**."
   <https://learningnetwork.cisco.com/s/question/0D53i00000Kt11lCAB/stp-timers>

2. **Cisco, "Understand and Tune Spanning Tree Protocol Timers" (doc 19120)** - "each BPDU includes the
   hello, forward delay, and max age STP timers ... Effectively, only a timer that is configured on the root
   bridge of the STP is important", and every timer change should be made "on the root bridge and on the
   backup root bridge". The same document gives the defaults and ranges (hello 2 s / 1-10, max age 20 s / 6-40,
   forward delay 15 s / 4-30).
   <https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/19120-122.html>

3. **howtonetwork, "Spanning Tree Timers"** - "Within the Spanning Tree domain, the only timer values that are
   important are those that are sent by the Root Bridge. In other words, **Non-Root Bridges are not concerned
   with locally configured timer values**", and, on the mechanism: "The newly selected root port and designated
   port must wait for two Forward Delay intervals before transitioning to the Forwarding state."
   <https://www.howtonetwork.org/switch/module-3/802-1d-spanning-tree-protocol-spanning-tree-timers/>

4. **The standard.** 802.1D-2004 section 17.14 carries the three defaults; the configuration BPDU (17.13, its
   `Hello Time`/`Max Age`/`Forward Delay` fields) is how they travel; 17.19 has a port's transition run one
   forward delay in each of Listening and Learning.

The captures in [stp-timer-lines-source.md](stp-timer-lines-source.md) agree from the other side: the
non-root in networkplayroom's lab *transmits* BPDUs every 10 s - the root's hello, not its own configured 2 -
which is only possible if the root's timers are the ones in force.

So: **two forward delays of the root's number**, on every bridge in the tree, root or not.

## What this model did, and what it does now

`engine/convergence.js` called `stpTimers(dev)` per device, so a lab whose root was given a 4 s forward delay
forwarded in 8 s on the root and 30 s on a non-root left at the default - while the non-root's own report
prints the root's `Forward Delay 4 sec` on its Root ID line (#1719, #1724). The report and the schedule
described two different networks.

Now:

- `stpTimersInForce(dev, rootDev)` returns the root's timers when `rootDev` is a different device, and the
  device's own otherwise. That is the one place the adoption rule lives.
- `stpRootOf(topo, stp, dev)` reads the root out of the election (`runStp()`), and answers null when there is
  no election to read, when the topology cannot name the device, or when this bridge's cost to the root is
  `Infinity`. The last case is deliberate: a bridge with no path to the root receives no BPDU, so nothing
  replaces its configuration and its own timers are what it runs.
- `buildSchedule()` takes the election as `opts.stp` and uses the timers in force, with the basis string
  naming the root when they are adopted (`listening + learning (4 s forward-delay each, the root SW1's)`).
  `stpPortStateAt()` takes the timers as a fourth argument for the same reason.
- `stpAdoption(topo, stp, dev, opts)` dates the window: the instant the box starts running the timers in force,
  which is `max(dev.bootedAtMs, root.bootedAtMs)` when it is its own root or came up with/before the root, and
  one configured hello after its own boot when it powers on into a tree already running. `buildSchedule()` adds
  that offset to `readyAtMs` and puts `adoptedAtMs` on the entry; `stpPortStateAt()` answers the seconds before
  it from the device's *own* `stpTimers(dev)`, because until the BPDU arrives the box believes it is the root.
- `Simulator.getConvergence()` passes `this.stpResult`, and `computeStp()` paces its transitional states the
  same way. With no election in hand the schedule reads each device's own configuration - the same fallback the
  header block makes when it has no root to quote.
- `setLinkState()`'s `reconvergeAtMs` was `atMs + stpTimers({}).forwardAtMs`, i.e. always +30 s. It is now the
  schedule's own STP completion, so the console's "Network converges again at N ms" and the schedule beside it
  are one number. A link between two boxes that run no bridge keeps the old +30 s, because there is no STP step
  to wait for.

`test/stp-root-timers-pace-the-tree.test.js` (43 assertions) pins: a 4 s root paces a 15 s non-root to 8 s; a
20 s non-root is still paced to 8 s while its Bridge ID line prints 20; a 4 s *non-root* under a default root
does not speed the tree up; a lone switch uses its own; a partitioned bridge falls back to its own and the
schedule says so; and the reconvergence reply equals the schedule's STP entry. `test/stp-adoption-window.test.js` (35 assertions) pins the window:
the same-instant pair costs nothing, a root up at 5 s is heard at 5 s, a non-root up at 5 s under a root up at 0
waits one hello (15 s, not 8), the hello counted is the root's, a cable moving elsewhere is not charged another
one, and a box powered on after the change owes no Max Age.

## What remains unresolved

- **When the adoption happens is a bound, not a measurement.** A real bridge uses the root's timers from the
  first configuration BPDU it accepts, so a non-root that boots before the root runs its own numbers for the
  interval before that. `stpAdoption()` dates it: the root's own boot when the two come up together (a port
  transmits a configuration BPDU the moment it becomes designated, so there is nothing to wait for), and one
  configured hello when the box powers on into a tree already running - the worst case for the root's next
  BPDU. What is still absent is a BPDU *arriving*: no per-port queue, no message age, so the instant is
  derived from two boot fields and one timer rather than observed, and a capture of
  `debug spanning-tree events` on both sides of a power-on would replace the constant. The other end of the
  window is settled: a box that loses the root *indirectly* holds the old root's BPDU for `Max Age` before it
  claims the root role - see [stp-max-age-hold.md](stp-max-age-hold.md).
- **The hello is counted once.** It prices the wait of a bridge that powers on into a running tree, and nothing
  else: hellos are not sent per port, so the interval between a change and the root's next BPDU is not modelled.
  A box that already holds a BPDU pays nothing for a change, which is the right answer reached the short way -
  it never lost what it was holding.
- **MSTP / RSTP are out of scope.** Both still take the timers from the root, but RSTP's proposal/agreement
  handshake replaces the listening/learning wait on point-to-point links, and this console refuses the
  per-instance commands by name. If RSTP is ever modelled, the two-forward-delay figure here becomes the
  fallback rather than the rule.
- **A non-default forward delay is only reachable from a device's config today.** This console has no
  `spanning-tree forward-time` verb (it answers with the bridge-priority refusal), so the rule is exercised by
  fixtures rather than by an operator typing a command.

## The state reads the window

The duration and the window that gives it a start are two different facts, and only the first was modelled.
`buildSchedule()` re-bases every entry at the instant of the change, but `stpPortStateAt()` compared the
*absolute* clock with `forwardAtMs`, so the answer to "what state is this port in at 60 s" came from a
transition that had begun at t=0. A cable moved at 60 s left every port the new tree had just unblocked
reading Forwarding the same instant, while the same change answered "Network converges again at 68000 ms";
with the Max Age hold in the schedule (#1746) the error went the other way and the port read Learning through
the seconds it should have spent Blocking. The entry now carries `startedAtMs` and `stpPortStateAt()` counts
from it (Blocking during the hold, then Listening, Learning, Forwarding at `readyAtMs`), and `setLinkState()`
records the change before it rebuilds the tree, because the rebuild is the thing that asks the schedule what it
is recovering from.

The instant the *first* BPDU is accepted is now modelled too - `stpAdoption()`, the first bullet under "What
remains unresolved" - and it is the other half of the same story: the state a port is in is counted from the
instant its box starts running the timers that pace it, whether that instant is a cable moving (an entry's
`startedAtMs`) or a bridge hearing the root for the first time (`adoptedAtMs`). Still outside the model: no
per-port BPDU and no message age, so the adoption instant is derived rather than observed; and the global re-base
at the end of `buildSchedule()` is unchanged - one cable anywhere still re-starts every bridge's clock, including
the bridges whose own ports did not move.
