# `show running-config`: is a VLAN's generated name written to the file?

**Question (one, narrow).** In `show running-config`, does the `vlan <id>` line carry the name a box makes
up for itself when nobody typed one (`VLANxxxx`, and `default` for VLAN 1), and where does a name somebody
*did* type sit? This asks only about the presence and placement of that name. It does not ask whether the
VLAN stanza appears at all on a factory switch (that is VTP, and PacketForge has no VTP - see
`research/extended-vlan-creation-vtp.md`), nor about any other line in the file.

**Verdict: the generated name is not written; a typed name is, in a ` name` sub-line one space in.** The
presence half is settled by Cisco's own capture of a switch in VTP transparent mode, which lists never-named
VLANs as `vlan 20-21,50-51` with no ` name` sub-line, in a stanza that does carry the sub-lines a box really
holds (` tb-vlan1 1002`). The placement half is settled by two independent lab transcripts that both print
`vlan 10` and then ` name RED`. PacketForge printed `vlan 44 VLAN0044`: the generated name written back into
the file, on the same line as the id. The name is now printed only when it differs from the generated one.
The placement was **not** changed, because it cannot be: `name` is a vlan sub-mode command and this console
has no vlan sub-mode, so the one-line form is the only form its own parser can replay.

## What the device prints

Cisco, *Maintain VLAN.DAT File on Catalyst Switches*, "Viewing VLAN Information" - the same page states the
rule ("The VLAN information and the VTP information are not displayed in the `show running-config` command
output when the switch is in the VTP server/client mode") and then shows the transparent-mode file:

```
Switch#show run | include vlan
vlan internal allocation policy ascending
vlan 1
 tb-vlan1 1002
 tb-vlan2 1003
vlan 20-21,50-51 
vlan 1002
 tb-vlan1 1
 tb-vlan2 1003
vlan 1003
 tb-vlan1 1
 tb-vlan2 1002
vlan 1004
vlan 1005 
```

<https://www.cisco.com/c/en/us/support/docs/switches/catalyst-2940-series-switches/109304-manage-vlandat.html>

Three things in that block matter here. `vlan 1` has no ` name default`. The four VLANs 20, 21, 50 and 51 are
one line with no name after them - and a box can only fold four VLANs onto one line when nothing about them
differs, so none of the four carries a name of its own. And the stanza is not write-only-for-ids: VLANs 1 and
1002-1003 do carry sub-lines (` tb-vlan1 1002`), one space in, so the printer has somewhere to put a name and
does not use it for the one it generated. (The trailing space after `vlan 20-21,50-51 ` and `vlan 1005 ` is
in the page's own preformatted text.)

The default itself, from the Ethernet VLAN defaults table: `VLAN name` = *VLANxxxx*, "where *xxxx* represents
four numeric digits (including leading zeros) equal to the VLAN ID number", and `name vlan-name` in config-vlan
mode is "(Optional) ... If no name is entered for the VLAN, the default is to append the vlan-id with leading
zeros to the word VLAN".

<https://cisco.com/c/en/us/td/docs/switches/lan/catalyst2960/software/release/12-2_58_se/configuration/guide/2960scg/swvlan.html>

A typed name, and its placement, from a lab walkthrough whose two switches' files are transcribed as
preformatted text:

```
SwitchX# show running-config
...
vlan 10
 name RED
!
vlan 20
 name ORANGE
!
vlan 30
 name BLUE
```

<https://www.practicalnetworking.net/stand-alone/configuring-vlans/>

That page is also the plainest statement of the mechanism behind the name, one paragraph earlier: assigning
`switchport access vlan 30` to a port "creates the VLAN with a generic name - the name for VLAN 30 above
defaults to `VLAN0030`". The name exists whether or not it was typed; what the file holds is what was typed.

Arista states the mechanism as a rule for the same command, one vendor over: "The **no name** and
**default name** commands restore the default name by removing the **name** command from *running-config*."

<https://www.arista.com/en/um-eos/eos-virtual-lans-vlans>

## The one capture that disagrees, and why it does not settle it

A configuration list printed in a paper on parsing device configurations carries VLAN lines with the
generated name written out:

```
15 vlan 30
16 name VLAN0030
17 exit
...
32 vlan 20
33 name VLAN0020
```

<https://www.arxiv.org/pdf/2511.17948>

This is recorded rather than explained away. It is not a transcript: it is a numbered extract presented as
"a portion of a network device configuration", with no prompt, no `show` command and no device or release
attached, so there is nothing to say whether the names were generated by the box or typed by whoever built
the example (typing `name VLAN0030` is exactly what a person does when they want the file to show a name).
It is the only source found that writes a generated name, and it cannot be checked against the device it
came from. Cisco's capture above can be checked, is a whole stanza, and shows the opposite.

## What PacketForge did, and what changed

Measured on `a0f06707` (main), `C2960X-48FPS-L`, in one session:

```
sw1(config)# interface Gi1/0/7
sw1(config-if)# switchport access vlan 44
% Access VLAN does not exist. Creating vlan 44
sw1(config-if)# exit
sw1(config)# vlan 60 name lab
VLAN 60 created (name: lab)
sw1# show running-config
vlan 10 VLAN0010
vlan 44 VLAN0044
vlan 60 lab
```

Two of those three lines name a VLAN with the value the box would have generated, and one of them is for a
VLAN no command ever named. After the change:

```
vlan 10
vlan 44
vlan 60 lab
```

The rule is one comparison in the running-config printer (`engine/cli.js`, the VLAN table just after the
`show running-config` handler's own header): the name is emitted when it differs from the generated one for
that id (`VLAN` + four digits, `default` for VLAN 1). Nothing else moved - the database still stores the
generated name at creation (`_createVlanForPort`, and the `vlan <id>` handler), so `show vlan` and
`show vlan brief` print `VLAN0044` exactly as before, and a pasted file recreates the same name from the
same rule on the way back in.

`test/running-config-vlan-default-name.test.js` (18 checks) pins: the unnamed VLAN's bare line; the VLAN a
port assignment made; a typed name kept; a typed name that *equals* the generated one printing bare (the box
cannot distinguish the two, and neither can this one); numeric ordering of the ids; VLAN 1 never writing
`default`; the paste round trip restoring both names and an identical `show vlan brief`; and the named form
still being replayable. `test/vlan-auto-create.test.js` previously asserted the line `vlan 44 VLAN0044` and
now asserts `vlan 44`, with the reason recorded there.

## What is inferred

* **The generated name is a default, which is why it is not written.** A running-configuration holds what was
  configured; `show running-config all` is a separate command precisely because plain `show running-config`
  omits the values a box fills in for itself. A name that `no name` restores (Cisco: "To return the VLAN name
  to the default settings, use the `no name` ... command") is that kind of value.
* **A name equal to the generated one is indistinguishable from no name at all.** Neither capture shows the
  pair side by side, but the box stores one name field and the file's omission is decided by comparing it with
  the default, so `name VLAN0044` on VLAN 44 writes nothing. This console does the same by construction.
* **The rule holds for the auto-created VLAN too.** The capture's VLANs 20, 21, 50 and 51 were not necessarily
  created by hand, and the command that creates one implicitly (`switchport access vlan`) is the same command
  in both places. This is the weakest link in the chain: see below.

## What remains unresolved

* **The placement of a typed name.** A box writes `vlan 20` and then ` name twenty` one space in, because
  `name` is a config-vlan sub-mode command. PacketForge has no vlan sub-mode - `name twenty` typed on its own
  line is refused with a sentence saying so, and `vlan 20 name twenty` is its one-line form. Adopting the
  sub-line would print a file this console cannot paste back, which is the one property these lines exist for;
  the remedy is a config-vlan mode, which is a feature, not a fidelity fix. `research/extended-vlan-creation-vtp.md`
  already records the same wall from the creating side.
* **VLAN range compression.** Cisco's capture folds VLANs 20, 21, 50 and 51 onto `vlan 20-21,50-51`, and
  `vlan 20-21` needs a syntax this console has for `switchport trunk allowed vlan` but not for `vlan`. Not
  touched: one line per id is the form that replays here, and the *presence* question is what this run asked.
* **Whether a VLAN made by `switchport access vlan` materialises its name.** The `vlan database` mode's own
  receipt prints `VLAN 30 added: Name: VLAN0030`, which is a *vlan.dat* record, not a running-config line -
  and this console's auto-create path is the closest thing it has to that door. If a future capture shows a
  transparent-mode file writing ` name VLAN0030` for a VLAN that a port assignment created and nobody named,
  the comparison in the printer is the one line to revisit.
* **What would settle it:** on a modelled platform (2960-X 15.2(7)E, or a 9200 at 17.18), in VTP transparent
  mode: `vlan 30`, `end`, `show running-config | include vlan`, then `interface X` / `switchport access vlan 31`
  for a VLAN that does not exist, and `show running-config | include vlan` again, then `vlan 30` / `name
  VLAN0030` and the same show. A capture of all three states settles the presence rule, the auto-created case
  and the typed-equal-to-generated case at once.
