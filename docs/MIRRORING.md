# Forgejo and GitHub: one source of truth, two front doors

Development, CI and CD live on **Forgejo**. GitHub is kept as a mirror so that people who already
have a GitHub account can read the code, clone it, and contribute without first creating an account
somewhere unfamiliar. This document describes what can be synchronised, what cannot, and the rule
that keeps the two from fighting.

The short version:

| Thing | Syncable? | How |
|---|---|---|
| Commits, branches, tags | **Yes, fully, one way** | Forgejo → GitHub push mirror |
| Pull requests | **No — bridge instead** | A job mirrors GitHub PR heads into Forgejo PRs |
| Issues and comments | **No — pick one tracker** | Forgejo is the maintained tracker (24 open), but GitHub is where issues are actually filed: 787 open there today, and nothing redirects them — see §3 |
| CI / CD | **Forgejo only, authoritative** | GitHub gets a courtesy subset at most |
| Wiki **source pages** | **Yes, with the repo** | `docs/wiki/*.md` is committed and regenerated by `npm run wiki:build`; it travels with every git push |
| The rendered **Wiki** on either forge | **No** | Each forge keeps its wiki in its own `<repo>.wiki.git`; a repo push mirror never touches it. Forgejo's is published by `npm run wiki:publish` (manual), and GitHub's would need its own mirror |

## The rule: one writer, one reader

Every failure mode in this area comes from symmetric sync. If both sides can write `main`, then two
force-pushes race, the loser's history is orphaned, and neither platform can be trusted about what
"the code" is. So:

- **Forgejo writes.** All merges, all tags, all releases.
- **GitHub reads.** It receives every commit and serves it to the public.
- **Contributions from GitHub flow in as branches that Forgejo merges.** They never arrive by
  pushing to the mirror directly.

## 1. Git: Forgejo → GitHub push mirror

Forgejo repo → **Settings → Repository → Push mirrors → Add push mirror**:

- Remote: `https://github.com/Jaylouisw/packetforge.git`
- Auth: a **fine-grained GitHub token**, repository `Jaylouisw/packetforge`, permission
  *Contents: read and write*. Nothing else. Store it in Forgejo's mirror config, not in the repo.
- Sync on commit: **on**, plus the scheduled interval as a backstop.

This copies every branch and tag. What it does *not* copy: issues, PRs, discussions, releases, wiki,
labels, milestones. Those are not git.

Measured on 2026-11-12, and the "every branch" half holds exactly: **884 heads on the forge, 884 on
GitHub**, and `refs/heads/main` is `73718ab4` on both. That is worth recording because the branch
count is not small and it moves — 872 earlier the same day, then 875, then 881, now 884, twelve more in
the hours between — so a mirror that copied only `main` would look healthy from a single-branch check.

Read "every branch" as **every branch on the forge**, which is not the same as every branch in your
clone: the working copy this was measured from carries **968** local heads, 84 of them never pushed.
The mirror compares the two servers, so a branch that exists only on a developer's disk is invisible to
it and no count of your own refs will ever match.

The tag half is untested rather than proven: there are **zero tags and zero releases** on either
side, so "every tag is copied" is vacuously true and nothing has ever exercised the path. Take the
release sentence in §4 (*"the mirror's tags are enough"*) as a plan rather than a description.

Verify:

```bash
# The forge side, on a host where `origin` (ssh://forgejo) resolves. It does NOT resolve in a sandbox:
# `git ls-remote origin` there fails with "Could not resolve hostname forgejo", and piped into `wc -l`
# that failure reads as a count of 0 — the mirror looking empty rather than unreachable. Use the HTTP
# remote or the public URL instead; both are reachable from anywhere.
git ls-remote --heads https://github.com/Jaylouisw/packetforge | wc -l                        # 884 today
git ls-remote --heads http://odin:3000/jaylouisw/packetforge.git | wc -l                     # same count, or the mirror is behind
git ls-remote https://github.com/Jaylouisw/packetforge refs/heads/main                      # 73718ab4
git ls-remote http://odin:3000/jaylouisw/packetforge.git refs/heads/main                     # same SHA, or the mirror is behind
git ls-remote --tags https://github.com/Jaylouisw/packetforge | wc -l                        # 0, so the tag half is untested
```

`https://git.jayw.uk/jaylouisw/packetforge` answers identically to `odin:3000` — same 884 heads, same
`73718ab4` — which is the cheapest check that the public host and the HTTP remote are the same instance.
Both URL spellings work: with and without the trailing `.git` return the same counts and the same SHA.

`origin` is an SSH alias on a developer machine, so the count only works where that alias resolves;
`git ls-remote` against `https://github.com/...` needs no credentials either way, which is how the
numbers above were taken.

**Never add the reverse direction.** A GitHub→Forgejo mirror plus a Forgejo→GitHub mirror is a loop;
whichever syncs second wins, and on a force-push they can ping-pong indefinitely.

## 2. Pull requests: bridged, not mirrored

Neither platform mirrors PRs, and there is no setting that makes it happen. A bot does it:

1. Poll GitHub for open PRs (`GET /repos/:owner/:repo/pulls?state=open`).
2. For each, fetch the head: `git fetch --force https://github.com/<owner>/<repo>.git
   refs/pull/<n>/head:refs/heads/gh/<n>`. This works for fork PRs on a public repo — `refs/pull/N/head`
   exists on the *base* repository even when the PR comes from a fork.
3. Push `gh/<n>` to Forgejo and open (or update) a PR titled `[gh#<n>] <title>`, body linking the
   original and crediting the author, with a `<!-- gh-pr: N -->` marker in the body.

   The branch is **`gh/<n>`**, not `gh-pr/<n>`: an earlier version of this page wrote the second form,
   and the script has only ever written the first (`const branch = 'gh/' + pr.number`). Anyone
   scripting against this should read `scripts/gh-bridge.js` rather than this list.
4. **Forgejo CI runs and is the gate.** Review happens on the Forgejo PR.
5. On merge, the push mirror updates GitHub, and `--report` comments the outcome on the GitHub PR.

Two mechanisms this list used to describe wrongly, both read off the script:

- **Idempotency is keyed on the marker, not the head SHA.** `indexByMarker(existing, /<!-- gh-pr: (\d+) -->/)`
  finds the Forgejo PR that already carries this GitHub number, so a contributor pushing twice updates
  one Forgejo PR rather than opening a second. The head SHA appears only as prose in the PR body —
  `Branch \`gh/<n>\` carries their commits verbatim (head <sha12>)` — and nothing branches on it.
- **The comment says what happened, in its own words**, not `Landed as <url>`:

  ```text
  Merged on the forge as <PUBLIC>/<repo>/pulls/<n> (commit <sha12>). It is already on GitHub main — the mirror pushes automatically.
  ```

  It is posted once: the report pass first asks GitHub whether any comment already contains
  `/pulls/<n>` and skips the PR if one does, so re-running `--report` does not stack comments.

The bridge does **not** close anything. It reads closed Forgejo PRs to find merges; the GitHub PR is
left for a human, because a bot closing PRs on a read-only mirror is a policy decision rather than a
sync step.

What the GitHub contributor sees: they open a PR the way they always do, and once a maintainer runs
`--prs` a bot replies **on that run** with a link to where the discussion is — not within a few
minutes, which is what this paragraph claimed while the status note further down explains that
nothing schedules the bridge. Their commits are there from that moment, not before.

What they cannot do: press "Merge" on GitHub. That button is meaningless on a mirror — the mirror is
a copy, and merging there creates a commit that the next mirror sync will not contain.

> **Status: the bridge script exists, the job that runs it does not.** `scripts/gh-bridge.js` is
> written and idempotent — `--issues` imports GitHub issues, `--prs` turns a GitHub pull request into
> a `gh/<n>` branch plus a Forgejo PR, `--report` comments the merge back on GitHub, and every
> imported object carries a `<!-- gh-issue: N -->` / `<!-- gh-pr: N -->` marker so re-running never
> duplicates. What is missing is the scheduled Forgejo workflow that invokes it: `.forgejo/workflows/`
> contains only `ci.yml` and `auto-rebase.yml`, so today the bridge is a command a human runs. Until
> that job exists, a GitHub PR stays invisible to this project unless somebody notices it.

Operating it, as measured on this tree. The script takes its configuration from four variables, none of
which any document names: `PF_FORGEJO_URL` (default `http://127.0.0.1:3000`), `PF_FORGEJO_TOKEN`,
`PF_FORGEJO_REMOTE` (default `forgejo`) and `PF_FORGEJO_PUSH_URL`. Every mode — `--issues`, `--prs`,
`--report`, `--all`, and `--dry-run` on top of any of them — **exits 2 with `PF_FORGEJO_TOKEN is required.`**
when the token is absent; only a bare invocation gets as far as `Nothing to do. Use --issues, --prs,
--report or --all (add --dry-run first).`, also with status 2. So "run it in dry-run first" is not a way to
try it without credentials.

Two defaults do not fit this repository, and would surprise anyone following the flags. The URL default
points at `127.0.0.1:3000`, while this worktree reaches the same Forgejo as **`http://odin:3000`**. And
`PF_FORGEJO_REMOTE` defaults to a remote name, `forgejo`, that **does not exist here** — the two remotes are
`origin` (`ssh://forgejo/…`, an alias that resolves only on the maintainer's host) and `forgejo-http`. It
turns out not to matter: the name is used once, as `PUSH_URL || REMOTE` at the push call, and `PUSH_URL` is
derived from the URL plus the token, so it is non-empty exactly when the token check has already passed.
`PF_FORGEJO_REMOTE` is therefore read and never effective; `PF_FORGEJO_PUSH_URL` is the knob that works.

## 3. Issues: one tracker, not two

Two-way issue sync needs a stateful bot holding an ID map, and it duplicates on every edit, delete
and label change. It is not worth the machinery, and half-working it is worse than not doing it.

**Forgejo is the tracker — in intent, and only partly in fact.** Measured on 2026-11-12: this forge
carries **24 open issues**, the GitHub mirror carries **787 open issues and 2 open pull requests**
(`api.github.com/search/issues` with `is:issue is:open`). Every issue on file here is labelled and
swept by `request-queue.js`; nothing on GitHub is. CONTRIBUTING sends contributors to GitHub because
accounts here are not open to the public, so the queue that grows is the one nobody triages — the top
table's row used to say "GitHub issues point at it", which was never true and is contradicted by the
paragraph below explaining that the redirect workflow does not exist. For GitHub:

- Migrate the open issues once (title, body, labels, author, created date). The API can do this;
  Forgejo's `POST /repos/:owner/:repo/issues` preserves the body and labels, and the original author
  and date are recorded in a header line of the body, since neither platform will backdate.
- Then a small GitHub Actions workflow comments on each new issue:
  *"This project tracks issues on Forgejo: <link>. Please reopen there — this one will be closed."*
  and closes it. It must *execute* on GitHub, because GitHub is where the issue is — but the
  **file** has to live in this repository — and `/.github/workflows/` does not exist today, having been
  deleted in #1059 (§4), so creating it is part of the job — and then be pushed out: GitHub is a push mirror, so a workflow committed on GitHub itself is overwritten by the
  next sync. Editing the mirror's issue *settings* is safe, because settings are not files.

An alternative that some projects choose: keep GitHub issues open as a **read-only archive** and
disable new ones (Settings → Features → uncheck Issues). Blunter, but it cannot be misunderstood.

## 4. CI and CD: Forgejo only

`.github/workflows/` **no longer exists** — it was deleted in #1059. While it was there, its jobs
were gated with `if: github.server_url == 'https://github.com'`, which meant they also ran on
Forgejo, where they failed every time with `docker: command not found` because the runner has no
Docker-in-Docker. Two pipelines, one of which could never pass. `.github/` now holds only the issue
and pull-request templates, labels and dependabot.

- `.forgejo/workflows/` is the authoritative pipeline: tests, syntax, examples, server smoke, the
  invariants.
- On GitHub, keep at most a **courtesy subset** (`npm test` + syntax) so a GitHub contributor sees
  red or green before the bridge picks their PR up. It must never be a merge gate, and the README
  says so.
- Releases and images are built on Forgejo and pushed to a registry both sides can pull from. GitHub
  Releases are not mirrored; the mirror's tags are enough.

## 5. The public door

None of this works while the canonical host is behind a login. `https://git.jayw.uk` used to
redirect anonymous visitors to Cloudflare Access, which made the repository, the issues and the
badges unreadable. That is **fixed**: an anonymous `GET` now returns `200`, and the arrangement that
did it — a host-wide bypass application for `git.jayw.uk`, leaving Forgejo's own login as the write
gate — is documented in [PUBLIC-ACCESS.md](PUBLIC-ACCESS.md), including how to re-apply it.

Cloudflare Zero Trust → Access → Applications → the app covering `git.jayw.uk`:

- Add a policy: **Bypass**, Include **Everyone**, scoped to the whole host.
- Leave **Allow** (your IdP rule) on everything else: `/admin`, `/api`, other repos.

A path-scoped bypass (`jaylouisw/packetforge*`) was tried first and removed: it made browsing work
but left `git clone` dead, because clones go through `/jaylouisw/packetforge.git`.

Check it from outside your own network — a phone on mobile data, not this machine:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://git.jayw.uk/jaylouisw/packetforge   # want 200
curl -s -o /dev/null -w '%{http_code}\n' https://git.jayw.uk/jaylouisw/packetforge/badges/workflows/ci.yml/badge.svg
```

302 to `cloudflareaccess.com` means the bypass is not matching. Also enable anonymous read on the
repository if the instance default is private (Settings → Advanced → *This repository is private*).

## 6. What this repo enforces

- `scripts/canonical.js` — the single definition of where the project lives. Change it there.
- `scripts/check-canonical-urls.js` — fails the build if any tracked file points at the old GitHub
  repository, or if the README's clone URL and CI badge do not match the canonical base. It found
  three stale links plus two scripts still calling `gh` the first time it ran. Measured on this tree it
  prints `OK — 2278 files, every project URL points at https://git.jayw.uk/jaylouisw/packetforge` and
  exits `0`. The figure is **not** a file count you can quote: the checker walks the *working tree* for
  seven extensions (`.md .js .json .yml .yaml .html .txt`), skipping `.git`, `node_modules`, `dist`,
  `coverage` and dot-directories other than `.github`/`.forgejo` — which means an untracked probe in
  `tmp/` counts too. It read `2266` this morning, `2268` an hour later, `2269` a few minutes after
  that and `2278` now, each time because someone added a file. Re-run it rather than quoting the number. `test/canonical-urls.test.js` holds **43** assertions — three of which plant a fault
  and require the checker to refuse it: a GitHub URL, a `gh` instruction, and a README that cannot be
  cloned from. That is what makes it a test rather than a pass.
- `scripts/forgejo-api.js` — the tracker client the triage scripts use instead of `gh`. A missing
  token is reported as *"the tracker is not readable without it (this is not the same as \"no open
  requests\")"* and the calling script exits **2** — measured on `request-queue.js`, which prints
  `Could not read issues from jaylouisw/packetforge.` and then that sentence. Never as *"no open
  requests"*: an unreadable tracker and an empty one are different answers, and only one of them
  means you can stop working.

  Measured with the token unset, the whole exchange is two lines and a status:

  ```
  $ node scripts/request-queue.js
  Could not read issues from jaylouisw/packetforge.
  FORGEJO_TOKEN is not set - the tracker is not readable without it (this is not the same as "no open requests")
  $ echo $?
  2
  ```
- `test/canonical-urls.test.js` — proves the checker can fail, so it is not a test that passes
  because it checks nothing.
